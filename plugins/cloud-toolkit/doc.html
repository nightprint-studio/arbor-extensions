Cloud Toolkit

The parts of object storage that are the same whichever store you use: splitting keys, matching wildcards, working out which byte ranges a large transfer needs, and deciding what a sync would actually do. It talks to nothing — it only computes.

You install it because the cloud panel asks for it, not because it does anything on its own. It has no panel, no settings and no commands.

What it can reach

Nothing. No network, no filesystem, no credential slots — its manifest declares no permissions at all, and there is nothing to grant it. A package that only computes cannot be talked into reaching something.

What it provides

FunctionWhat it answers
plan-ranges The byte ranges a transfer of a given size should ask for. The last one is short rather than past the end; an empty object plans nothing.
glob-match Whether a key matches a pattern. ? is one character and * any run — neither crossing / — while ** crosses, so a search in one folder stays there unless you ask otherwise.
order-chunks Split parts in the order they were split in, by number or by date. Stores list lexicographically, where part10 comes before part2 — which concatenates a split archive into a corrupt file.
sync-plan What a download would create, update, skip or delete, and how many bytes that moves — decided before anything is transferred, so it can be shown to you first. Compares on size, modification time and etag; never reads a file's contents.
split-key · join-key · parent-prefix Key handling that treats a/b/c.txt as one key with slashes in it, which is what it is.
encode-segment · rfc3339-secs URL encoding for keys, and the timestamp format every store answers in.

Why it exists as a package

None of this is Arbor's to know. A host that carried it would be a host that had learned what a bucket is, and at that point the cloud stops being a plugin and becomes a built-in feature with a plugin attached.

It is also not a provider: a provider talks to one service, and this talks to none. It is the shared library both sides use — a provider compiles it in, and the panel calls this component — so the two can never disagree about what part10 sorts after.

Calling it from a plugin

Through the extension seam, like any other package: 

local plan = arbor.ext.call{
  interface = "cloud-util", id = "core", method = "sync-plan",
  args = { remote, local_files, { overwrite = "if-newer", ["delete-extraneous"] = false } },
}
for _, action in ipairs(plan.actions) do
  -- action.create / update / skip / delete
end

Calling an extension needs service_call in your own package's [permissions]: it is invoking another package's code, and that is the permission that says so.
