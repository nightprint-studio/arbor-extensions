Google Cloud Storage

Adds GCS buckets to Arbor's cloud panel. This package is the backend — the panel, the connection list and the settings form live in the cloud-storage package, which this one depends on. Installing this without that one gives you a provider with nothing to drive it; the Marketplace offers to install both.

Before you connect: your own OAuth client

Google issues an OAuth client per application, and a client id shipped inside a package would be shared by everyone who installed it — one quota, one consent screen, one thing to revoke. So this package asks for yours.

  1. Create a Desktop OAuth client at console.cloud.google.com/apis/credentials.
  2. Register http://127.0.0.1:7732/ as its redirect URI.
  3. Paste the client id (and secret, if it issued one) into either place — they are the same client: the OAuth fields on the connection itself, under Cloud → Connections, or this package's settings, the gear beside it in the Plugin Manager. A client entered on a connection is stored here, so the next sign-in and every later refresh find it.

Connecting

Open Cloud → Connections → Add, pick Google Cloud Storage, and sign in. A browser window opens; approve, and come back. The refresh token is stored in your operating system's keychain, never in a settings file and never inside this package's folder.

Already signed in with the Google SDK?

If you have run gcloud auth application-default login, this package finds those credentials and uses them — pick Application Default Credentials as the method and there is nothing else to set up. It reads that one file and never writes to it.

ADC comes in two shapes and both work: a user grant, which is refreshed like any sign-in, and a service-account key, which is adopted and used as below.

Service-account keys

A connection set to service account file keeps only the file's path. The panel reads the file each time a token is needed and passes its contents in that one call; this package signs with it and keeps nothing of it — only the access token it buys is stored. The rest of this section is about a key pasted into the form.

Paste the key file's contents into the connection form. It is stored in this package's own keychain slot — the panel that took it from you does not keep a copy, because it is not the thing that can use it.

Using it is one exchange: the key signs a short-lived assertion, and the assertion buys an access token that lasts an hour. The signing happens inside the sandboxed component, which is the only place in Arbor with the cryptography for it — the key is handed to the component and to nothing else, and never leaves this machine.

Who runs the sign-in

This package does — not the cloud panel. It owns the credential slot, and a package can only reach the slots its own manifest declares, so the token can only be written by the thing that reads it. It is also what keeps the panel free of Google: the panel asks this package to connect, by name, and never learns which endpoints or scopes were involved.

What Arbor lends is the part no package can hold: the loopback listener the browser comes back to, and the keychain. The endpoints, the scope and Google's own consent parameters are arguments this package passes.

What it can reach

Exactly two things, both declared in its manifest and both shown to you when you install it:

  • Network: googleapis.com and its subdomains. Nothing else — a request to any other host is refused by Arbor before it is sent.
  • Two credential slots — the access token, and the service-account key if you use one. It can read and write those two and no others, and it cannot name the credentials Arbor keeps for itself (your git provider tokens, your issue-tracker keys) at all.
  • Read access to one file, the application-default credentials the Google SDK writes. Nothing is ever written there.

The backend is a sandboxed WebAssembly component: it has no filesystem, opens no sockets, and never handles TLS. Every request is performed by Arbor on its behalf, which is what makes the two limits above enforced rather than promised.

What it supports

OperationNotes
BrowseFolders are synthesised from key prefixes — object storage has no directories. A folder row has no size or date because there is none to report.
DownloadRead in ranges, so progress and Cancel stay with the panel — the transfer is the panel's, only the bytes come from here. A large file is a sequence of ranges appended to one file, and the bytes never pass through the panel itself.
UploadWhole-object per call, so a large upload is sent in slices of the local file. Each slice is one call; the panel decides how big they are.
DeleteRemoving a key that is not there succeeds.
CopyServer-side — the bytes never travel through your machine.
