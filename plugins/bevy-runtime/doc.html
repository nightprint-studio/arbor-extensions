Bevy runtime

A 3D viewport that any plugin can open. It ships once and is shared, so a plugin that needs to draw something does not have to carry a game engine of its own — which would otherwise be tens of megabytes per plugin, downloaded separately, built separately.

Scenes are documents

What it draws is described by a .ron file, in the same dialect used across fulcrum's content: a camera rig, a light rig, an environment, and the entities to place. The runtime reads the document and builds it. It has no idea what a shader preview is.

That is what makes it extensible without being a monolith. A compiled Bevy app cannot load Rust at runtime, so if a scene were a function, adding one would mean rebuilding and reshipping this package. Adding a scene is adding a file.

Holes

A scene declares what it does not know as Param("name"). The shader preview scene, for instance, leaves the WGSL, the mesh and the material parameters to whoever opens it — which is how one scene serves every plugin that wants to look at a material, without the scene knowing where any of it came from.

Real Bevy, not an approximation

The shader you give it is compiled by Bevy itself, so #import bevy_pbr::… resolves against the real shader library and apply_pbr_lighting is the real one. What you see is what ships. A translator would have had to stand in for that frame, and a stand-in is a different picture.

What it can reach

Nothing. No network, no filesystem, no credentials. It runs in a frame with an opaque origin — no storage, no cookies, no access to the application around it — and the only way in or out is the message channel the host provides.

Installing it on its own

Nothing happens: it draws when a plugin opens a scene in it. Install it because something else asked for it.
